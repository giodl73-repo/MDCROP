# MDCROP Pitfalls

## MDCROP-PF-01: Context Pack Becomes Answer Authority

**Status:** OPEN

**Pattern:** A selected MDCROP pack is treated as semantic closure or the final
answer, even though it is a bounded evidence proposal.

**Domain:** Agent handoff, RAG workflows, README claims, generated docs, and
future customer demos.

**Actor:** Agent author, RAG builder, doc generator, customer-demo author, or
future consumer of a generated context pack.

**Task:** Use an MDCROP pack to brief an agent or reader while deciding whether
the selected evidence is enough to answer a question.

**Surface:** CLI view output, generated packs, README examples, benchmark
reports, PROOF artifacts, and downstream prompt/context handoffs.

**Likely mistake:** Treat the selected pack as semantic closure or final answer
authority because it is compact, readable, and generated by a tool.

**Consequence:** An agent or reader can stop checking excluded files, bridge
evidence, provenance, or missing counterexamples and answer from a bounded
proposal as if it were the whole corpus.

**Owner:** MDCROP context-boundary cartographer, RAG builder, and downstream
consumer owner.

**Detection difficulty:** Focused packs are useful and compact, so users may
stop checking whether excluded evidence changes the answer.

**Structural solution:** Keep context-boundary roles and benchmark metrics
focused on evidence selection, not answer correctness.

**Evidence:** `.roles/parliament/context-boundary-cartographer.md`,
`.roles/stakeholders/rag-builder.md`, `PRODUCT_PLAN.md`, and
`docs/BENCHMARKS.md`.

**Test:** `cargo test -p mdcrop-core --test pitfall_policy`.

## MDCROP-PF-02: Fixture Win Becomes General Retrieval Superiority

**Status:** OPEN

**Pattern:** MDCROP fixture and benchmark wins are generalized into broad
retrieval superiority claims without real-corpus and competitor-method evidence.

**Domain:** Product claims, paper evidence, benchmark reports, and customer
positioning.

**Actor:** Research author, benchmark maintainer, README editor, customer-demo
author, or release reviewer.

**Task:** Describe MDCROP benchmark results while deciding whether fixture
performance supports broad retrieval, RAG, or competitor-superiority claims.

**Surface:** `docs/BENCHMARKS.md`, examples under `examples\competitors`,
generated benchmark output, product plan, README claims, and paper notes.

**Likely mistake:** Generalize deterministic fixture wins into broad retrieval
superiority before real-corpus runs and competitor-method evidence exist.

**Consequence:** Public or customer-facing claims can overstate MDCROP's
validated benefit and make fixture overfitting look like retrieval science.

**Owner:** MDCROP retrieval-benchmark skeptic, README surface editor, and
research author.

**Detection difficulty:** The fixture suite is intentionally compelling and
deterministic, so it can sound broader than its controlled setup.

**Structural solution:** Require Retrieval Benchmark Skeptic review plus
explicit fixture/real-corpus separation in claims.

**Evidence:** `.roles/parliament/retrieval-benchmark-skeptic.md`,
`docs/BENCHMARKS.md`, `examples/competitors/`, and `cargo test --workspace`.

**Test:** `cargo test -p mdcrop-core --test pitfall_policy`.

## MDCROP-PF-03: Consumer Adoption Pin Becomes Compatibility Guarantee

**Status:** OPEN

**Pattern:** PROOF, MAXIM, or another consumer's current MDCROP invocation is
treated as a compatibility guarantee for future schema, CLI, or output changes.

**Domain:** PROOF generated docs, MAXIM large-corpus recipes, portfolio
dependency adoption, and release notes.

**Actor:** PROOF publisher, MAXIM recipe maintainer, dependency adopter,
release-note author, or future CLI/schema editor.

**Task:** Reuse a current MDCROP invocation while deciding whether future
schema, CLI, side-info, strict semantics, or view behavior can change safely.

**Surface:** Consumer integration specs, PROOF artifact specs, local large
corpus recipes, named views, release notes, and portfolio dependency records.

**Likely mistake:** Treat a working consumer example or pinned invocation as a
standing compatibility guarantee for all future MDCROP changes.

**Consequence:** A CLI, schema, view, or side-info change can break PROOF,
MAXIM, or another consumer because the repo skipped consumer-specific
rehearsal.

**Owner:** MDCROP view-contract keeper, proof-publisher stakeholder, and
affected consumer owner.

**Detection difficulty:** Consumer examples can keep working locally while
their implied contract is broader than the tests actually rehearse.

**Structural solution:** Require consumer-specific rehearsal before changing
stable schema names, strict semantics, view behavior, or side-info reports.

**Evidence:** `docs/specs/consumer-integration-options.md`,
`docs/specs/proof-artifacts.md`, `.roles/stakeholders/proof-publisher.md`, and
`.roles/parliament/view-contract-keeper.md`.

**Test:** `cargo test -p mdcrop-core --test pitfall_policy`.

## MDCROP-PF-04: Checked View Store Depends On Local Corpora

**Status:** MITIGATED

**Pattern:** Machine-local MAXIM or Resonance recipes live in `examples\views`,
so the documented strict store check fails when those corpora are not present
at hard-coded local paths.

**Domain:** View inspection, agent validation, CI gates, local examples, and
research-paper replay.

**Detection difficulty:** The recipes passed on machines with the corpora, and
non-strict inspection still printed a useful report before failure.

**Structural solution:** Keep portable checked recipes under `examples\views`
and machine-local large-corpus recipes under `examples\local-views`.

**Evidence:** `README.md`, `docs/VIEWS.md`, `cargo run -p mdcrop-cli -- view
--inspect --dir examples\views --strict`, and `git diff --check`.

## MDCROP-PF-05: Ordinary Tests Hide Strict Static-Analysis Debt

**Status:** MITIGATED

**Pattern:** `cargo test --workspace` passes while `cargo clippy --workspace
--all-targets -- -D warnings` fails on test-target layout or command-boundary
shape.

**Domain:** Rust maintainability, CLI command APIs, release validation, and
portfolio scoring.

**Detection difficulty:** The behavior is correct and tests pass, so the debt
appears only when the stricter analysis gate is part of the PITFALL pass.

**Structural solution:** Include clippy with warnings denied in MDCROP PITFALL
validation and keep command entry points grouped behind option structs when
argument lists grow.

**Evidence:** `crates/mdcrop-core/src/lib.rs`,
`crates/mdcrop-cli/src/status.rs`, `crates/mdcrop-cli/src/main.rs`, and
`cargo clippy --workspace --all-targets -- -D warnings`.
